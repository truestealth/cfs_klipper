# Участие в разработке

[English](CONTRIBUTING.md) | Русский

1. Подготовьте окружение по [быстрому старту](README.ru.md#быстрый-старт).
2. Создайте ветку для небольшого законченного изменения.
3. Добавьте небольшой регрессионный тест для исправленной ошибки или тест нового поведения.
4. Запустите проверки из корня проекта в активированном окружении:

   ```sh
   python -m unittest discover -s tests -v
   ```

5. Обновите затронутую документацию на английском и русском вместе.
6. Откройте Pull Request с описанием проблемы, изменения и способа проверки.

Исходники находятся в `src/cfs_box/`, точка входа Klipper — в `klipper/`,
тесты — в `tests/`. Используется стандартный `unittest`; имена файлов начинаются
с `test_`. Тесты запускаются прямо из рабочей копии без установки пакета.
Описывайте неочевидное поведение в docstring, а причины технических решений —
в комментариях. Делайте небольшие изменения без постороннего рефакторинга.

Перед реализацией CFS прочитайте [архитектуру](docs/architecture.ru.md),
[протокол](docs/protocol.ru.md) и [покрытие совместимости](docs/compatibility.ru.md).
Расширение рассчитано на Python 3.8 или новее. Сохраняйте штатный транспорт `serial_485`;
проверяйте конкретный путь native API вместо открытия второго serial-соединения.
Текущий загрузчик намеренно отклоняет активацию.

Тесты загрузки и native-вызовов добавляются вместе с соответствующими реализациями.
Проверяйте отсутствие показаний, отрицательные ответы и таймауты, а не только ACK.
Тесты на ПК используют синтетические данные и не обращаются к оборудованию.
Результат на ПК не считается аппаратной приёмкой. Модули и синтетические примеры
добавляются по необходимости для подтверждённого поведения; пустые модули
и упаковка самостоятельного приложения не нужны.

Используйте синтетические тестовые данные. Не включайте в PR закрытые бинарники,
сырые результаты анализа, учётные данные, личную информацию и настройки конкретной
машины. Отличайте проверенную совместимость от предположений и неподдерживаемого поведения.
