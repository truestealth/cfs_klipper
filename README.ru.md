# Creality Filament System (CFS) Box for Klipper — Open Source Edition

[English](README.md) | Русский

Открытая замена штатного модуля Klipper `[box]` для Creality K1C с K1 Series CFS
Upgrade. Сохраняем прошивку MCU CFS, экран, Creality Print, статус Fluidd,
маппинг слайсера и пользовательские настройки.

Существующая хостовая библиотека `serial_485` сохраняется. Объём работы — полный
штатный контракт `box`: инициализация, загрузка, выгрузка, резка, смена и продувка,
пауза/продолжение, ошибки/восстановление, датчики, RFID и данные катушек.

Базовая прошивка MCU нашего CFS — **1.1.3**. В
[истории изменений прошивки](docs/compatibility.ru.md#firmware-history) описаны
изученные отличия до 1.5.3 и их значение для совместимости.

**Статус:** компоненты хоста, поддерживаемые маршруты загрузки, смены инструмента,
печати, дозаправки и восстановления имеют проверки на ПК. Этап 9 добавляет
интеграцию с сохранёнными потребителями, тесты Jinja-макросов и обратимый установщик
файлов для разработки. Локальная проверка также исполняет закреплённые исходники
сохранённых Python-модулей и макросов с заменой аппаратных действий; публичный CI
использует синтетические примеры.

`load_config` теперь загружает `[box]` в **пассивном режиме допуска**: доступны
чтение идентичности и телеметрии, а действия хоста и native-записи заблокированы.
Переключателя механики в конфигурации или G-code нет. См.
[поведение первого запуска](docs/installation.ru.md#passive-startup).
Аппаратная приёмка и сверка текущей конфигурации ещё предстоят.
Два изученных сохранённых макроса загрузки не передают обязательный физический
`TNN`: выполнение останавливается до загрузки. Текущий этап сохраняет наблюдаемую
проверку отображения в `START_PRINT` и передачу аргументов обеими обёртками,
повторяя исходное поведение. Оптимизацию и исправления рассмотрим позже, если
потребуется. Зафиксированные результаты не означают успешную печать или загрузку.

## Структура проекта

```text
src/cfs/        Реализация расширения
klipper/box.py  Тонкая точка входа Klipper
tests/          Проверки на ПК
docs/           Архитектура, протокол и совместимость
```

Этап 1 дал матрицу полного контракта. Этап 2 добавил состояние, настройки,
хранение и девять обработчиков команд данных. Этап 3 добавил вызовы сохранённого
native API, проверку ответов, точные профили прошивок и двенадцать обработчиков
native-команд. Этап 4 добавляет явное подключение ready/shutdown, reconnect,
heartbeat, защищённые ожидания операций и общую обработку ошибок. Этап 5
добавляет настроенные движения, вентиляторы, нагрев, подачу, резку, очистку
и калибровку. Этап 6 добавляет предзагрузку, загрузку и выгрузку. Этап 7
добавляет смену инструмента и жизненный цикл печати. Этап 8 добавляет runout,
восстановление и продолжение. Зарегистрированы все 103 имени команд: 101 обычная
и две условные Hall-команды. Старая команда подачи остаётся заблокированной.
Этап 9 проверяет интеграцию и обратимое размещение файлов. Кодировка 0, wire-этапы
выше семи, зарезервированные операции и безадресная диагностика остаются
неподдерживаемыми; точные открытые пути перечислены в матрице.

- [Архитектура](docs/architecture.ru.md): ответственность и размещение в Klipper.

## Быстрый старт

Тесты запускаются прямо из рабочей копии стандартным `unittest`. Установите
[requirements-test.txt](requirements-test.txt): Jinja2 3.1.6 нужен только тестам
рендеринга макросов; расширение не устанавливается как пакет. **Python 3.8 — версия проекта
по умолчанию**, указанная в [.python-version](.python-version). Перед тестами
создайте локальное окружение с CPython 3.8. Совместимость с native-средой MIPS
и принтером пока не проверена.

Windows / PowerShell:

```powershell
py -3.8 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-test.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Linux / macOS:

```sh
python3.8 -m venv .venv
.venv/bin/python -m pip install -r requirements-test.txt
.venv/bin/python -m unittest discover -s tests -v
```

Готовую `.venv` с Python 3.8 можно использовать повторно. Если установлен `uv`,
вместо команды создания окружения можно выполнить `uv venv --python 3.8 .venv`.

Тесты покрывают снимки состояния и remap, все 54 настройки и 21 поле endpoint,
команды данных, временные файлы, native-запросы и ответы, разные версии устройств
и устаревшие действия, загрузчик и целостность матрицы. Проверки жизненного цикла
охватывают адресный heartbeat, shutdown/restart, паузу/сообщения и head-событие
внутри ожидания native-запроса. Проверки движений и подачи используют
синтетические координаты, вентиляторы, нагреватели и отсчёты колеса; проверки
резки различают свежее событие датчика и кэш, а также резку без датчика.
Тесты не исполняют штатный native-бинарник и не управляют оборудованием. См. [покрытие и намеренные отличия
хранения](docs/compatibility.ru.md#state-configuration-and-storage)
и [правила действий хоста](docs/compatibility.ru.md#host-actions), а также
[ограничения интеграции жизненного цикла](docs/protocol.ru.md#lifecycle-integration).

## Разработка

[Workflow CI](.github/workflows/ci.yml) настроен на те же тесты на Python 3.8
и читает тот же файл версии и тестовые зависимости. CI проверяет установку
и откат во временных каталогах, без развёртывания на принтере и сборки дистрибутива. Правила участия —
в [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md).

В сообщении об ошибке укажите коммит, окружение, версии хоста/MCU и шаги
воспроизведения. Удаляйте секреты, личные идентификаторы и частные захваты.
