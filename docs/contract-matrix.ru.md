# Матрица полного контракта

[English](contract-matrix.md) | Русский

**Этап 1:** инвентаризация и привязка проверок завершены.
[Машинно-читаемая матрица](contract-matrix.json) содержит **422 требования**
и **96 семейств проверок**: 78 на ПК и 18 на оборудовании. Компоненты данных,
native/версий, жизненного цикла/ошибок/контекста и отдельные механические
действия проверяются на ПК: 21 семейство реализовано, 35 частичны,
40 запланированы. Полные смены инструмента, восстановление и аппаратная приёмка ещё предстоят.
Целостность каталога сама по себе не устанавливает функциональную совместимость.

База — MCU CFS **1.1.3**, штатный `serial_485.so` и конфигурация нашего K1C
с CFS Upgrade. Различия известных MCU учитываются внутри общей реализации.

Строка — требование, не обязательно команда или отдельная тестовая функция.
Шаблоны статуса/датчиков `Tn` явно охватывают T1–T4, массивы слотов идут в порядке
A/B/C/D. Шаблоны статуса охватывают 69 конкретных путей ключей, включая четыре
контейнера боксов. Каждая настройка и поле endpoint имеют свою строку. Значения
по умолчанию описывают изученный загрузчик и не перезаписывают настройки принтера.

## Как читать и поддерживать матрицу

Каталог JSON содержит общие для обеих версий документа технические формулировки
на английском. Постоянные ID связывают требования, проверки и открытые вопросы:

| Поле | Значение |
| --- | --- |
| `id`, `kind`, `name` | Постоянный идентификатор, поверхность и имя интерфейса/поведения |
| `parameters`, `when` | Синтаксис/defaults/типы/границы и применимая конфигурация либо условие регистрации |
| `contract` | Требуемое наблюдаемое поведение или сохраняемая граница владения |
| `stage` | Этап реализации из [плана](implementation-plan.ru.md), а не номер стадии на шине |
| `checks` | ID сценариев PC/HW; каждый разрешается в конкретные утверждения каталога |
| `evidence` | `static`, `partial` либо в дальнейшем `hardware`; отдельно от реализации |
| `implementation` | `pending`, `partial` или `implemented`; статус компонента отделён от аппаратной приёмки |
| `implementation_note` | Граница частичной реализации или намеренное отличие от оригинала |
| `blockers` | Применимые открытые вопросы; в `gaps` перечислены затронутые строки и критерии закрытия |
| `code`, `alias_of` | Числовой код команды/статуса либо зарегистрированный алиас, где применимо |

Например, `CMD-BOX_SET_PRE_LOADING` связан с проверками параметров, native-вызовов
и preload. `MACRO-INFO-REFRESH` добавляет требование: обновление данных потребителем
вызывает preload RUN. `OP-HEAD-CALLBACK` связывает взаимодействие stage4/stage6
со сценариями времени callback, отказа и аппаратными проверками.

Семейства проверок имеют `status: planned` с `test: null` либо
`partial`/`implemented` со списком запускаемых ссылок, например
`tests/test_state.py::StateTests.test_raw_getters_and_distinct_sentinels`.
Частичное семейство также содержит оставшиеся утверждения `remaining`.
Тест каталога проверяет существование указанного метода; запуск набора
устанавливает локальный результат. Пустая функция, сохранённый внешний макрос
или регистрация команды не считаются реализованной механикой.

Сейчас отмечены 235 реализованных требований, 72 частичных и 115 ожидающих.
Общие контракты, которым также нужны полные механические операции или восстановление,
остаются частичными.
[Примечания совместимости](compatibility.ru.md#state-configuration-and-storage)
описывают разделение кэша/наблюдений, ошибки и намеренные правила сохранения;
[native-интеграция](protocol.ru.md#native-integration) фиксирует реализованную
границу и ограничения исполнения. [Примечания жизненного цикла](protocol.ru.md#lifecycle-integration)
описывают новые компоненты и принятые правила. Регистрация обработчиков не завершает
общие контракты: явно зарегистрированы 55 команд, включая одну заблокированную
старую команду, и два условных Hall-обработчика.

## Найденные связи с макросами

Матрица учитывает активные определения в изученных копиях конфигурации,
порядок include/override, переименованные алиасы, передачу параметров,
переменные макросов и потребителей `printer.box`:

| Взаимодействие | Требуемая проверка |
| --- | --- |
| `rename_existing` | Базовые команды существуют до установки алиасов на `klippy:connect`; сохраняется порядок include/override |
| `NEXT_FILAMENT` и две обёртки `_99` | Сохраняются температурная переменная и точная передача `rawparams` через обёртки подачи/продувки |
| Макросы загрузки с материалом/без него и выгрузки | Сохраняются разные последовательности фаз, ожиданий материала и обработки ошибок |
| `BOX_INFO_REFRESH ADDR=... NUM=...` | Preload RUN предшествует RFID/остаткам; операция механически активна, а `M400` не доказывает физическое завершение |
| Активный `START_PRINT` | Сохраняются проверка `INITIAL_TOOL`, нагрев перед T, начальная продувка и существующее переопределение старта |
| Завершение/отмена | Сохраняются `BOX_END` перед `BOX_END_PRINT`, общая очистка и базовые алиасы |
| Пауза/resume | Сохраняются `POST_WORK=0`, порядок `BOX_ERROR_CLEAR` и `BOX_RESUME_EXTRUDE`, переменные и передача скорости resume |
| Определения runout | Сохраняется маршрутизация primary/head из изученной конфигурации, включая выбор владельца по `printer.box.enable` |
| Исполнение шаблонов | Снимок при рендеринге отличается от последующего исполнения G-code; у вложенных вызовов свои границы |
| Сохранённый диагностический потребитель статуса | Для этого потребителя сохраняются агрегатный `state` перед вложенными и наблюдаемый порядок версий T1–T4 |

Это контракты взаимодействия с существующими макросами, помощниками материалов/
диагностики и определениями датчиков. Их файлы и службы остаются у текущих
владельцев. Имя внешнего макроса не регистрируется за новой реализацией только
из-за префикса `BOX_`. Копии подтверждают изученное содержимое; перед установкой
определяется фактически активная конфигурация принтера.

## Прямые Python-потребители

Сохранённые модули принтера также обращаются к объекту box напрямую.
Перечень изученных целевых Python-исходников выявил обязательные пути:

- `box.box_state.is_continue_print`;
- `box.box_action.box_state.Tn_data['enable']`;
- `box.box_action.box_save.move_z` и `.last_err`;
- `box.record_tn_move_z(value)`, включая вызов с нулём;
- `box.box_state.tn_save_data_path`;
- `box.inside_error`, который наблюдает сохранённое ожидание отмены;
- `box.box_action.heart_process_enable`, который наблюдает адресатор.

Отложенная цель resume принадлежит **`virtual_sdcard.resume_tnn`**.
Hook записи Z передаёт метаданные файла печати с `tn_move_z`; это отдельный
интерфейс от движения. Сохраняются пути и их общее изменяемое состояние,
без требования копировать прежнюю иерархию классов. Глубокая копия статуса
не заменяет внешне изменяемое рабочее состояние. Приёмочные утверждения
зафиксированы в `PC-RETAINED-BOX-API`.

У клиентских ошибок есть отдельное требование `ERROR-REPORT-API`: сохранить
`!! {code,msg,values}`, обработку повторов/специальных ключей, guard ошибки
и зависящие от контекста действия паузы/после паузы.

## Решения и открытые вопросы исполнения

| Вопрос | Необходимое разрешение |
| --- | --- |
| `GAP-LEGACY-13` | Установить callers и поведение запроса хоста с двумя байтами данных при ожидании MCU одного; принять решение о совместимости до исполнения маршрута |
| `GAP-STAGES` | Проверить преобразование публичных стадий и legacy triggers; диапазон STAGE не устанавливает номера поддержанных стадий на шине |
| `GAP-OPTIONAL-POSITIONS` | Пустой ответ endpoint восстановлен и проверен на ПК; проверить оставшиеся движения/resume при включённых/выключенных позициях |
| `GAP-SERIAL-NAME` | Решено: использовать только настроенный bus, исключив исторический избыточный lookup фиксированного имени. Базовое и альтернативное имя проверены на ПК |
| `GAP-HEAD-SENSOR-NAME` | Решено: использовать настроенный датчик для lookup и всех enable-путей. Без настроенного датчика сохраняется отдельный True fallback и не отправляются G-code включения датчика |
| `GAP-RESERVED-WIRE` | Отделить три резервных идентификатора от выдуманных прямых API; восстановить необходимый путь перед использованием |
| `GAP-MACRO-SNAPSHOT` | Зафиксировать активную include-цепочку и отпечатки конфигурации перед приёмкой на принтере |

Пять вопросов остаются открытыми; правила lookup serial и датчика головы определены. Открытые
вопросы ограничивают соответствующие пути. Запись вопроса завершает пункт
инвентаризации, но не реализацию и не подтверждение успеха механики.

## Заводской reference и доказательства целевой сборки

Официальный [репозиторий K1 Series Klipper](https://github.com/CrealityOfficial/K1_Series_Klipper/tree/e09f36e6ada60e5467b0bef731a96263b5d8095b)
закреплён на `e09f36e6ada60e5467b0bef731a96263b5d8095b`. Его опубликованный
[движок макросов](https://github.com/CrealityOfficial/K1_Series_Klipper/blob/e09f36e6ada60e5467b0bef731a96263b5d8095b/klippy/extras/gcode_macro.py)
устанавливает правило переименования на `klippy:connect`. Опубликованные макросы
K1C и virtual SD служат заводскими справочными источниками окружающих интерфейсов.

В шести проверенных деревьях веток/тегов отсутствуют CFS-специфичные исходники
box, serial, адресатора и box-конфигурации. В опубликованном обычном обработчике
датчика нет события головы целевой CFS-сборки. Сравнённые конфигурационные файлы
также не совпадают целиком с целевыми копиями. Поэтому матрица различает заводские
references, анализ целевых бинарников и снимки конфигурации; имя официального
репозитория не устанавливает состав установленной CFS Upgrade сборки. Копии
источников, значения конкретного принтера и сырой анализ остаются вне каталога.

Официальная [CFS-интеграция K2](https://github.com/CrealityOfficial/K2_Series_Klipper/tree/bc0a52078ace1e4d82995e396b38457b9f441024)
закреплена отдельно. Опубликованный образ CFS G32 1.1.3 побайтно совпадает с
изученной базой. Его [исходник датчика головы](https://github.com/CrealityOfficial/K2_Series_Klipper/blob/bc0a52078ace1e4d82995e396b38457b9f441024/klippy/extras/filament_switch_sensor.py)
также совпадает с сохранённой целевой копией: custom event при истинном состоянии
отправляется после RunoutHelper, включая его ранний возврат. Поэтому callback
box требует собственных проверок контекста операции и повторного события.
`BOX_INFO_REFRESH` также совпадает с изученной целевой последовательностью.

У K2 другой native ABI (ARM/CPython 3.9 против целевого MIPS/CPython 3.8),
настройки датчиков и механические процессы. Его библиотеки, дополнительные
команды, координаты резака и конфигурации не принимаются за настройки K1C
Upgrade. Совпадение MCU-образа не устанавливает совместимость хостовых модулей.

## Проверки, доступные сейчас

Запуск существующего набора прямо из рабочей копии:

```sh
python -m unittest discover -s tests -v
```

`test_contract_matrix.py` проверяет конечные перечни, ID, этапы, реальные ссылки
на тесты, алиасы, условную регистрацию, вопросы и счётчики покрытия. Частичные
и планируемые сценарии отделены от завершённых семейств проверок.
Тесты состояния/настроек/хранения и команд данных исполняют синтетические
сценарии и операции во временных файлах. Наборы native, протокола, прошивок
и интеграции box проверяют байты запросов, все разбираемые статусы, payload,
разные идентичности и устаревшие действия через подстановки. Проверки жизненного
цикла/ошибок/контекста добавляют кооперативные ready/shutdown, reconnect, heartbeat,
сообщения и head-событие внутри native-вызова.
Тесты движения, подачи и резки проверяют настроенные команды, ограничения,
состояние вентиляторов, подстановки нагревателя и колеса, события датчика и
отказы калибровки. Поведение штатного производителя
события и полное потребление результата загрузкой отделены от этих проверок
компонентов. Проверка загрузчика
подтверждает отказ от доступа к объектам принтера. Эти тесты не исполняют штатный
бинарник и не управляют оборудованием.

Статусы реализации/проверки — в [compatibility.ru.md](compatibility.ru.md),
граница native API — в [protocol.ru.md](protocol.ru.md).
