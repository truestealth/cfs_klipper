# Протокол и контракт штатного serial

[English](protocol.md) | Русский

**Статус:** этап 3 реализует вызовы заимствованного native-объекта, разбор ответов
и выбор версии каждого устройства; проверки выполняются с подстановками на ПК.
Загрузчик продолжает отклонять активацию. Сохранённый `.so` и принтер этими
проверками не выполнялись; полный цикл замены K1C ещё не подтверждён.

Постоянные якоря разделов позволяют ссылаться на документ из реализации и тестов.
Перед использованием команды в операции сюда добавляется её подтверждённое
описание для нужной версии.

## Границы и доказательства

Реализованный путь заимствует настроенный serial-объект Klipper через
восстановленный API. Транспортом и формированием кадров занимается штатная
библиотека. Документ описывает границу API и формат на шине; собственной
реализации транспорта здесь нет.

| Обозначение | Значение |
| --- | --- |
| Проверено на ПК | Воспроизводимая проверка указанных данных или ветки кода; не аппаратный результат |
| Частично | Есть часть доказательств, но версия или поведение на целевой системе установлены не полностью |
| Неизвестно | Достаточных доказательств для указанного поведения целевой системы нет |

Каждый вывод относится к фактически изученным версиям хоста/MCU и операции.
Совпадения opcode недостаточно. Оригинальные бинарники и приватные исследования
остаются вне публичных исходников. [Матрица контракта](contract-matrix.ru.md)
ссылается на разрешённые официальные заводские источники и связывает полный
хостовый интерфейс с проверками.

<a id="native-integration"></a>

## Реализованная native-интеграция

Явная привязка получает `serial_485 <настроенный bus>` и заимствует этот объект.
Она не открывает UART, не подключает/отключает native serial и не забирает его
очереди и таймеры. Флаг транспортного соединения не устанавливает наличие CFS.
`Request.body` содержит `ADDR LEN REQUEST_STATE CMD DATA`; обычный typed-запрос
использует state `0xFF`. F7/CRC для передачи добавляет штатная библиотека.
`Frame` сохраняет полный ответ и проверенные
адрес, команду, статус и payload. Неверные header, длина, CRC или принадлежность
ответа — ошибка, отдельная от `None` и отрицательного статуса MCU.

Три уровня повторов остаются раздельными:

| Владелец | Условие и граница |
| --- | --- |
| Sender box | В обычных запросах проверенные MCU CRC/LENGTH ошибки вызывают до семи native API обменов при timeout ниже 3600, до трёх при 3600 и выше |
| Штатный wrapper | У выбранных команд есть собственные внешние попытки при `None`, до пяти; `retries_en=False` не убирает этот цикл |
| Штатный serial handler | Ожидание/повтор даёт до пяти попыток при включённых retries и timeout ниже 3600; иначе одну, с нижним ожиданием одной секунды при 3600 и выше |

Обычный вызов передаёт ровно `(body, timeout)`; явный флаг повторов остаётся
необязательным третьим аргументом. Здесь реализованы только обмены уровня box;
два сохранённых native-цикла восстановлены статически. Один API-вызов не равен
одной UART-передаче, а эти счётчики не задают deadline всей операции.
`COMMUNICATION_TEST` использует отдельный байт ответа, включая целочисленный
ноль, и не выполняет повторы по статусу MCU.

Поколения привязки и каждого адреса проверяются до каждой native API попытки,
после ожидания или ошибки и до/после каждого упорядоченного semantic effect.
Устаревший контекст останавливает дальнейшую обработку хостом; отложенные
callbacks также отклоняют старый контекст после отсоединения. Проверки не прерывают уже
идущий API-вызов и не отменяют его внутренние native-повторы.

Сообщение ошибок, пауза/восстановление, операции событий слотов и другие hooks
операций ещё требуют реальных lifecycle-обработчиков. Их отсутствие вызывает
`MissingProtocolEffect` до исполнения effects; тихая пустая заглушка не
устанавливает успех. Sender сохраняет контекстные результаты `True`/`False`/`None`.
ACK, telemetry и сохранённые сведения не устанавливают завершение загрузки или смены.

Исполнение блокирует все запросы opcode `0x13`, typed legacy encoding-0
`EXTRUDE_PROCESS`, typed stages выше 7 и безадресную диагностику (`ADDR=0`).
Подтверждённые wire stages — 0–7. Их соответствие публичным STAGE, именам фаз
хоста/журнала и полным операциям остаётся отдельным открытым вопросом. Raw
диагностика не превращает неизвестный payload в проверенную typed-операцию;
дополнительная `0x12` автоматически не выбирается.

Тесты [native](../tests/test_native.py), [декодера](../tests/test_protocol.py),
[прошивок](../tests/test_firmware.py) и [интеграции](../tests/test_box_native.py)
используют синтетические кадры и подстановки. Реальный native admission, число
передач, планирование и завершение механики остаются аппаратной приёмкой.

<a id="firmware-versions"></a>

## Требования к версиям прошивки

Текущая база — MCU CFS 1.1.3; 1.5.2 и 1.5.3 — дополнительные цели, ожидающие
аппаратной проверки. Статически сопоставлены также cfs0/G32 1.2.2, 1.4.2 и
1.5.0. В коде заданы точные профили **1.1.3, 1.2.2, 1.4.2, 1.5.0, 1.5.2 и
1.5.3**, без fallback для неизвестной версии.

Перед использованием особенностей версии читаем работающую прошивку через
сохранённый native API и храним исходный ответ версии/идентичности каждого бокса.
Имя файла в пакете или manifest обновления не доказывает, что выполняется в MCU.
Версия MCU отличается от прошивки принтера и настройки `[box] version`.

Изученный ответ `0x14` содержит ровно 22 байта данных: три ASCII-цифры версии
и 19 байтов серийного номера. Байты SN сохраняют штатное посимвольное
представление Latin-1, включая NUL и старшие байты, без обрезки. Исходный ответ
и точная версия с точками учитываются раздельно для каждого адреса.
Эта identity не определяет семейство продукта или аппаратный ID. Поддержанный
профиль требует отдельно подтверждённого контекста `cfs0` и точной известной
версии; `[box] version` не является таким подтверждением.

Повреждённый или неудачный запрос identity сбрасывает текущий профиль и
публичные version/SN, сохраняя исходную диагностику. Disconnect/rebind сбрасывает
текущую identity и требует нового чтения. После disconnect тот же SN может
повторно использовать явный контекст семейства; заменённый SN снимает это
подтверждение. Неизвестные семейства и прошивки не наследуют механику базовой версии.

Статически установлены четыре байта обычных данных `0x0A` в 1.1.3/1.2.2 и
шесть в 1.4.2/1.5.0/1.5.2/1.5.3. События слотов со статусом `0x30` сохраняют
четыре байта. Дополнительные поля обычного ответа нельзя принимать за события.
Изученные приложения 1.5.2/1.5.3 имеют одинаковое поведение обычных команд;
различаются параметры заводских тестов и метаданные версии. Это не аппаратная приёмка.

[Базовая версия и история изменений](compatibility.ru.md#firmware-history)
описывают накопленные отличия от MCU нашего CFS 1.1.3 до 1.5.3, включая RFID,
восстановление подачи буфера и дополнительную команду подачи.

Для каждой проверенной версии фиксируем форматы запросов/ответов, смысл статусов,
preload и стадийных операций, ограничения ожиданий и повторов. Обычные ответы
и события разбираются отдельно. Одинаковые длины запросов не доказывают
одинаковые ответы или механическое поведение.

Дополнительные команды включаются после проверки поддержки MCU и их работы
через сохранённый `serial_485.so`, включая зависящие от команды повторы.
Неизвестная прошивка остаётся явно неподдержанной для механических операций,
пока нужное поведение не установлено. Тесты и аппаратная приёмка указывают
точное сочетание версий, которое проверяют.

<a id="framing"></a>

## Формат кадра

**Доказательства: частично для целевой системы.** Геометрия кадров и CRC проверены
на ПК по сохранённым справочным данным. Работа native API целевой системы
и физическое завершение операции этим пакетом не проверены.

| Поле | Размер | Значение |
| --- | --- | --- |
| SYNC | 1 байт | `0xF7` |
| ADDR | 1 байт | Адрес назначения/ответа; важен контекст адресации |
| LEN | 1 байт | Число следующих байтов: STATUS + CMD + DATA + CRC |
| STATUS | 1 байт | Контекст запроса или статус ответа; зависит от команды и режима |
| CMD | 1 байт | Команда в контексте адреса/режима |
| DATA | N байтов | Данные конкретной команды |
| CRC | 1 байт | CRC-8 от LEN до конца DATA |

`LEN = N + 3`; полный размер кадра — `N + 6`, или `LEN + 3`.
Параметры CRC: полином `0x07`, начальное значение `0x00`, без отражения,
финальный XOR `0x00`. SYNC и ADDR в расчёт не входят.

Синтетический пример кадра: `F7 01 03 00 A2 DA`. DATA отсутствует;
CRC от `03 00 A2` равен `DA`. Пример показывает только геометрию и не является
указанием отправить команду адресации оборудованию.

Матрица фиксирует все 19 хостовых идентификаторов команд и 16 typed-схем
запросов. Резервные идентификаторы отделены от реализованных typed-операций.
Единицы механики и переходы стадий требуют собственной приёмки.

<a id="native-api"></a>

## API штатного serial

**Доказательства:** граница восстановлена по сохранённой библиотеке и проверена
через подстановки на ПК. Реальный целевой ABI, admission и тайминги ещё не проверены.

| Элемент | Изученная граница | Что требуется проверить |
| --- | --- | --- |
| Объект | Существующий объект Klipper для настроенной шины `serial_485` | Порядок инициализации и доступность на целевой системе |
| Метод запроса | `cmd_send_data_with_response(data, timeout, retries_en=True)` | Целевой ABI и реальное поведение для каждой нужной команды |
| Байты запроса | ADDR, LEN, STATUS, CMD, DATA; SYNC/CRC добавляет native-код | Команду и обработку длины на целевой системе |
| Ответ | Полный кадр при ответе, `None` после исчерпания попыток; исключения могут передаваться вызывающему коду | Поздние ответы, отрицательные статусы и разрыв связи на целевой системе |
| Повторы | Native-код может повторять отдельные команды даже при `retries_en=False` | Число передач и бюджет таймаута каждой команды |
| Доступ к приёму | Допуск ответов и callbacks ограничены native-реализацией | Наблюдения, доступные через поддержанный путь запросов |

Вызывающий код различает отсутствие ответа, отклонённый/некорректный ответ,
подтверждённый запрос и физическое завершение. Ответ не `None` не означает успех
операции. Нельзя считать флаг повторов гарантией единственной передачи,
а callbacks — доступом ко всем входящим кадрам. Соединением продолжает владеть Klipper.

## Покрытие операций

Полная спецификация охватывает инициализацию, соединение, загрузку, выгрузку,
резку, смену, продувку, паузу/продолжение, отказы/восстановление, датчики, RFID
и данные катушек. Для каждой группы нужны подтверждённые команды, наблюдения,
ожидания и отказы. Раздел загрузки ниже — часть этого полного контракта.

<a id="loading"></a>

## Загрузка

**Доказательства: полный маршрут замены не проверен.** При реализации используем
восстановленные команды, предикаты и выходы ошибок из матрицы. Таблица описывает
необходимое покрытие операций, а не успешный рабочий цикл.

| Фаза | Нужные сведения |
| --- | --- |
| Предварительные условия | Исходное положение филамента, наличие в слоте, готовность и температура |
| Подача CFS | Native-вызовы и обработка принятых/отклонённых ответов |
| Прибытие | Отдельные наблюдения CFS, буфера и головы; обработка отсутствующих данных |
| Подача экструдера | Согласование с существующими макросами, режимами и настроенными длинами |
| Продувка | Существующее настроенное поведение и условия завершения |
| Завершение | Свежие наблюдения, устанавливающие успех, и итоговое состояние |
| Отказ | Остановка/освобождение, ошибка, сохраняющаяся неопределённость и разрешённый повтор |

Не придумываем тайминги стадий и не переносим последовательность другой
модели/MCU. Сохраняем штатную политику preload;
настройка OPEN и действие RUN не взаимозаменяемы. Обновление RFID или слотов может
включать механику и не является пассивным запросом статуса.

<a id="timing"></a>

## Ожидания, повторы и отказы

Отдельно фиксируются таймаут транзакции, возможные native-повторы, общий срок
операции, ожидаемое удержание ответа и ожидание датчика. При реализации используем
монотонное время и ожидания, позволяющие reactor работать. Таймауты запросов
закодированы и проверены на ПК; фактические deadlines операций и время
восстановления целевого маршрута ещё не проверены.

Неизвестное показание датчика не превращается в успешную загрузку. Настроенный
материал, сохранённый активный слот или ACK не отменяют противоречивые физические
наблюдения. Покрытие реализации отражается в
[compatibility.ru.md](compatibility.ru.md).
