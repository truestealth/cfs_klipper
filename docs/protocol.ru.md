# Протокол и контракт штатного serial

[English](protocol.md) | Русский

Пакет называется `cfs`, объект Klipper — `box`. Он заимствует штатный объект
`serial_485` и запускается в пассивном режиме identity/телеметрии. На базовой MCU
CFS 1.1.3 проверены четыре предзагрузки и два последовательных полных цикла
загрузки/выгрузки T1C без ручной помощи.

Постоянные якоря разделов позволяют ссылаться на документ из реализации и тестов.
Перед использованием команды в операции сюда добавляется её подтверждённое
описание для нужной версии.

## Границы и доказательства

Реализованный путь заимствует настроенный serial-объект Klipper через
восстановленный API. Транспортом и формированием кадров занимается штатная
библиотека. Документ описывает границу API и формат на шине; собственной
реализации транспорта здесь нет.

| Обозначение | Значение |
| --- | --- |
| Проверено на ПК | Воспроизводимая проверка указанных данных или ветки кода; не аппаратный результат |
| Частично | Есть часть доказательств, но версия или поведение на целевой системе установлены не полностью |
| Неизвестно | Достаточных доказательств для указанного поведения целевой системы нет |

Каждый вывод относится к фактически изученным версиям хоста/MCU и операции.
Совпадения opcode недостаточно. Оригинальные бинарники и приватные исследования
остаются вне публичных исходников. [Матрица контракта](contract-matrix.ru.md)
ссылается на разрешённые официальные заводские источники и связывает полный
хостовый интерфейс с проверками.

<a id="native-integration"></a>

## Реализованная native-интеграция

Явная привязка получает `serial_485 <настроенный bus>` и заимствует этот объект.
Она не открывает UART, не подключает/отключает native serial и не забирает его
очереди и таймеры. Флаг транспортного соединения не устанавливает наличие CFS.
`Request.body` содержит `ADDR LEN REQUEST_STATE CMD DATA`; обычный typed-запрос
использует state `0xFF`. F7/CRC для передачи добавляет штатная библиотека.
`Frame` сохраняет полный ответ и проверенные
адрес, команду, статус и payload. Неверные header, длина, CRC или принадлежность
ответа — ошибка, отдельная от `None` и отрицательного статуса MCU.

Три уровня повторов остаются раздельными:

| Владелец | Условие и граница |
| --- | --- |
| Sender box | В обычных запросах проверенные MCU CRC/LENGTH ошибки вызывают до семи native API обменов при timeout ниже 3600, до трёх при 3600 и выше |
| Штатный wrapper | У выбранных команд есть собственные внешние попытки при `None`, до пяти; `retries_en=False` не убирает этот цикл |
| Штатный serial handler | Ожидание/повтор даёт до пяти попыток при включённых retries и timeout ниже 3600; иначе одну, с нижним ожиданием одной секунды при 3600 и выше |

Обычный вызов передаёт ровно `(body, timeout)`; явный флаг повторов остаётся
необязательным третьим аргументом. Здесь реализованы только обмены уровня box;
два сохранённых native-цикла восстановлены статически. Один API-вызов не равен
одной UART-передаче, а эти счётчики не задают deadline всей операции.
`COMMUNICATION_TEST` использует отдельный байт ответа, включая целочисленный
ноль, и не выполняет повторы по статусу MCU.

Поколения привязки и каждого адреса проверяются до каждой native API попытки,
после ожидания или ошибки и до/после каждого упорядоченного semantic effect.
Устаревший контекст останавливает дальнейшую обработку хостом; отложенные
callbacks также отклоняют старый контекст после отсоединения. Проверки не прерывают уже
идущий API-вызов и не отменяют его внутренние native-повторы.

Жизненный цикл предоставляет обработчики сообщений об ошибках, сохранённой
ошибки, тайм-аута, событий слотов и runout. Отсутствие необходимого обработчика
вызывает `MissingProtocolEffect` до исполнения effects. Sender сохраняет контекстные
результаты `True`/`False`/`None`.
ACK, telemetry и сохранённые сведения не устанавливают завершение загрузки или смены.

Исполнение блокирует все запросы opcode `0x13`, typed legacy encoding-0
`EXTRUDE_PROCESS`, typed stages выше 7 и безадресную диагностику (`ADDR=0`).
Подтверждённые wire stages — 0–7. Их соответствие публичным STAGE, именам фаз
хоста/журнала и полным операциям остаётся отдельным открытым вопросом. Raw
диагностика не превращает неизвестный payload в проверенную typed-операцию;
дополнительная `0x12` автоматически не выбирается.

Тесты [native](../tests/test_native.py), [декодера](../tests/test_protocol.py),
[прошивок](../tests/test_firmware.py) и [интеграции](../tests/test_box_native.py)
проверяют границу API, кадры и выбор версии.

<a id="lifecycle-integration"></a>

## Жизненный цикл, ошибки и контекст операции

`load_config` всегда регистрирует пассивный допуск: заимствованному native API
по умолчанию доступны только typed-чтения `0x02`, `0x03`, `0x05`, `0x08`, `0x0A` и `0x14`.
Raw-диагностика, запросы колеса, `CREATE_CONNECT` и записи заблокированы, как
и действия хоста. Автоматические preload/RUN, переключение датчиков, подача
головы, runout-подтягивание, пауза и нагрев подавлены. Сообщения сохраняют
клиентский текст без механических выходов обработки ошибки. Общего переключателя
механики нет. Отдельный [явный тест предзагрузки](installation.ru.md#single-operation-trial)
может разрешить один выбранный `0x0D` RUN без смены пассивного жизненного цикла;
владение запросом/контекстом не передаётся обычным командам и фоновым callbacks.
См. [зависимости запуска и пути данных](installation.ru.md#passive-startup).

В базовой MCU 1.1.3 `GET_RFID` (`0x02`) читает доступную запись слота;
физическое считывание RFID этот запрос не выполняет. Для слота с пластиком без
доступной записи возможен ответ `unknown`. В таком случае `GET_REMAIN_LEN`
(`0x03`) возвращает подстановку `100`: она не подтверждает полную катушку или
свежую оценку остатка. Оба ответа наблюдались на базовом устройстве. Хост
сохраняет известные цвета/материалы, записывая `vender=unknown`; ответы этих
getter-запросов поэтому могут заменить прежние сохранённые метаданные.
Полное считывание RFID/оценка остатка может двигать моторы и не запускается
пассивным допуском по умолчанию. Сохранённые ID метки и остаток нужно отличать от свежего
наблюдения MCU.

В обычном ответе базовой 1.1.3 `0x0A` байт `DATA[2]` содержит накопленную
диагностику моторов, потребляемую чтением состояния; режим находится отдельно
в `DATA[3]`. Биты 0–3 относятся к каналам A–D, бит 4 — к общему монитору малого
движения, бит 7 помечает доставку длительного условия.
Фоновый heartbeat может потребить признак до другого чтения.
Эти признаки отделены от физических выключателей и завершения операции.

Следующие правила операций описывают активный контракт компонентов, проверяемый
при явном создании на ПК. Регистрируются 101 обычная команда и две условные
Hall-команды. На `klippy:ready`
жизненный цикл получает зависимости, заимствует serial, отправляет `box:ready`
и затем запускает собственный таймер heartbeat. Наличие определяется по
`online == 1` адресатора и существованию serial-порта, независимо от флага
соединения native. При подключении сначала намеренно читается identity, чтобы
`0x0A` разбирался по правильному профилю. Переподключение требует новой identity;
другой серийный номер снимает подтверждение семейства. При инициализации
сохранённые метаданные слотов попадают в live-состояние только после свежего
успешного ответа датчика MATERIAL.
Подтверждение ранее неизвестного семейства или изменение известной версии
запускает новую попытку инициализации до возобновления обычного heartbeat-опроса.

Сообщённые режимы `0`–`5` означают IDLE, PRELOADING, PRINTING, WRAPPERING,
ERROR и TEST соответственно. Это не кодировка действия запроса `SET_BOX_MODE`.
Heartbeat опрашивает один разрешённый адрес за проход; `None` уменьшает его
счётчик от пяти, а `False` и ответы событий сбрасывают счётчик. При запуске
значение power-on preload `None` ожидается не более десяти интервалов по полсекунды;
`False` завершает ожидание. Терминальная ошибка heartbeat останавливает таймер
без автоматического перезапуска. Shutdown удаляет собственные задачи расширения
и отвязывает заимствованный объект, не закрывая native-транспорт. Поколения
привязки, устройства и операции останавливают устаревшее продолжение после
перепривязки или shutdown, в том числе после G-code и ожиданий.

Настроенный датчик головы одинаково используется агрегированным состоянием,
enable CFS и обработкой ошибки филамента. Без настроенного датчика наличие
использует штатный fallback `True`, а эти пути не отправляют G-code датчику.
Тайм-аут не сообщается, если сохранённое состояние адреса не `connect`, а
native-соединение установлено. Иначе ошибка сообщается; в `disconnect` переводится
только ранее подключённый адрес.

Сообщения сохраняют клиентскую схему, подавление дубликатов и специальные ключи,
сообщаемые без паузы. Обычные исключения при сообщении логируются, флаг снимается.
`inside_error` — наблюдаемый флаг обработки, не запрет повторного входа. Ошибка
во время печати может вызвать паузу и восстановление сохранённого состояния;
проверки после кооперативных действий останавливают устаревшее продолжение.
Контекст операции владеет целью и на время вооружённой фазы головы отключает
heartbeat только для её адреса. Он сохраняет результат и статус стадии 6 даже
при результате `False`; ни флаг, ни ACK не доказывают физическое завершение.
Отсутствующие или завершающиеся исключением действия фаз отменяют владение
и восстанавливают прежнее разрешение heartbeat. Фаза загрузки использует этот
сохранённый результат. Custom-событие головы отделено от debounce, отключения
и фильтрации повторов в RunoutHelper.

`slot_events` хранит диагностику каждого адреса; отдельный обработчик событий
слотов обновляет метаданные и планирует защищённые обновления. Power-on refresh,
движение головы и стадия 6 требуют переданных действий и явно завершаются ошибкой
при их отсутствии. Смена инструмента и восстановление проверены с подстановками,
но не на оборудовании.
См. [совместимость](compatibility.ru.md) и компонентные тесты
[жизненного цикла](../tests/test_lifecycle.py), [ошибок](../tests/test_errors.py)
и [операции](../tests/test_operations.py).

<a id="firmware-versions"></a>

## Требования к версиям прошивки

Текущая база — MCU CFS 1.1.3; 1.5.2 и 1.5.3 — дополнительные цели, ожидающие
аппаратной проверки. Статически сопоставлены также cfs0/G32 1.2.2, 1.4.2 и
1.5.0. В коде заданы точные профили **1.1.3, 1.2.2, 1.4.2, 1.5.0, 1.5.2 и
1.5.3**, без fallback для неизвестной версии.

Перед использованием особенностей версии читаем работающую прошивку через
сохранённый native API и храним исходный ответ версии/идентичности каждого бокса.
Имя файла в пакете или manifest обновления не доказывает, что выполняется в MCU.
Версия MCU отличается от прошивки принтера и настройки `[box] version`.

Изученный ответ `0x14` содержит ровно 22 байта данных: три ASCII-цифры версии
и 19 байтов серийного номера. Байты SN сохраняют штатное посимвольное
представление Latin-1, включая NUL и старшие байты, без обрезки. Исходный ответ
и точная версия с точками учитываются раздельно для каждого адреса.
Эта identity не определяет семейство продукта или аппаратный ID. Поддержанный
профиль требует отдельно подтверждённого контекста `cfs0` и точной известной
версии; `[box] version` не является таким подтверждением.

Повреждённый или неудачный запрос identity сбрасывает текущий профиль и
публичные version/SN, сохраняя исходную диагностику. Disconnect/rebind сбрасывает
текущую identity и требует нового чтения. После disconnect тот же SN может
повторно использовать явный контекст семейства; заменённый SN снимает это
подтверждение. Неизвестные семейства и прошивки не наследуют механику базовой версии.

Статически установлены четыре байта обычных данных `0x0A` в 1.1.3/1.2.2 и
шесть в 1.4.2/1.5.0/1.5.2/1.5.3. События слотов со статусом `0x30` сохраняют
четыре байта. Дополнительные поля обычного ответа нельзя принимать за события.
Изученные приложения 1.5.2/1.5.3 имеют одинаковое поведение обычных команд;
различаются параметры заводских тестов и метаданные версии. Это не аппаратная приёмка.

[Базовая версия и история изменений](compatibility.ru.md#firmware-history)
описывают накопленные отличия от MCU нашего CFS 1.1.3 до 1.5.3, включая RFID,
восстановление подачи буфера и дополнительную команду подачи.

Для каждой проверенной версии фиксируем форматы запросов/ответов, смысл статусов,
preload и стадийных операций, ограничения ожиданий и повторов. Обычные ответы
и события разбираются отдельно. Одинаковые длины запросов не доказывают
одинаковые ответы или механическое поведение.

Дополнительные команды включаются после проверки поддержки MCU и их работы
через сохранённый `serial_485.so`, включая зависящие от команды повторы.
Неизвестная прошивка остаётся явно неподдержанной для механических операций,
пока нужное поведение не установлено. Тесты и аппаратная приёмка указывают
точное сочетание версий, которое проверяют.

<a id="framing"></a>

## Формат кадра

Геометрия кадра и CRC проверены на ПК и в базовых ответах API.

| Поле | Размер | Значение |
| --- | --- | --- |
| SYNC | 1 байт | `0xF7` |
| ADDR | 1 байт | Адрес назначения/ответа; важен контекст адресации |
| LEN | 1 байт | Число следующих байтов: STATUS + CMD + DATA + CRC |
| STATUS | 1 байт | Контекст запроса или статус ответа; зависит от команды и режима |
| CMD | 1 байт | Команда в контексте адреса/режима |
| DATA | N байтов | Данные конкретной команды |
| CRC | 1 байт | CRC-8 от LEN до конца DATA |

`LEN = N + 3`; полный размер кадра — `N + 6`, или `LEN + 3`.
Параметры CRC: полином `0x07`, начальное значение `0x00`, без отражения,
финальный XOR `0x00`. SYNC и ADDR в расчёт не входят.

Синтетический пример кадра: `F7 01 03 00 A2 DA`. DATA отсутствует;
CRC от `03 00 A2` равен `DA`. Пример показывает только геометрию и не является
указанием отправить команду адресации оборудованию.

Матрица фиксирует все 19 хостовых идентификаторов команд и 16 typed-схем
запросов. Резервные идентификаторы отделены от реализованных typed-операций.
Единицы механики и переходы стадий требуют собственной приёмки.

<a id="native-api"></a>

## API штатного serial

Сохранённый API проверяется с подстановками на ПК и неизменённой базовой
библиотекой на MCU 1.1.3.

| Элемент | Изученная граница | Что требуется проверить |
| --- | --- | --- |
| Объект | Существующий объект Klipper для настроенной шины `serial_485` | Владение и доступность при других конфигурациях/отказах |
| Метод запроса | `cmd_send_data_with_response(data, timeout, retries_en=True)` | Поведение команд вне наблюдённых базовых путей |
| Байты запроса | ADDR, LEN, STATUS, CMD, DATA; SYNC/CRC добавляет native-код | Команду и обработку длины на целевой системе |
| Ответ | Полный кадр при ответе, `None` после исчерпания попыток; исключения могут передаваться вызывающему коду | Поздние ответы, отрицательные статусы и разрыв связи на целевой системе |
| Повторы | Native-код может повторять отдельные команды даже при `retries_en=False` | Число передач и бюджет таймаута каждой команды |
| Доступ к приёму | Допуск ответов и callbacks ограничены native-реализацией | Наблюдения, доступные через поддержанный путь запросов |

Вызывающий код различает отсутствие ответа, отклонённый/некорректный ответ,
подтверждённый запрос и физическое завершение. Ответ не `None` не означает успех
операции. Нельзя считать флаг повторов гарантией единственной передачи,
а callbacks — доступом ко всем входящим кадрам. Соединением продолжает владеть Klipper.

## Покрытие операций

Полная спецификация охватывает инициализацию, соединение, загрузку, выгрузку,
резку, смену, продувку, паузу/продолжение, отказы/восстановление, датчики, RFID
и данные катушек. Для каждой группы нужны подтверждённые команды, наблюдения,
ожидания и отказы. Раздел загрузки ниже — часть этого полного контракта.

<a id="loading"></a>

## Загрузка и выгрузка

[Явная проба загрузки/выгрузки](installation.ru.md#material-operation-trial)
владеет одним выбранным слотом и проверяет свежие состояния головы, хаба,
буфера, режима и источника. Она исполняет настроенный рецепт макросов с нагревом,
резкой, очисткой, продувкой и возвратом позиции. Жизненный цикл по умолчанию
остаётся пассивным.

### Предзагрузка

OPEN настраивает предзагрузку при включении, RUN выполняет её. Полное обновление
при включении запускает RUN перед запросами RFID/остатка. Пассивный допуск
разрешает typed-чтения, подавляя автоматический RUN и действия событий слотов.
[Проба предзагрузки](installation.ru.md#single-operation-trial) проверяет базовый
режим и свежие MATERIAL/CONNECTIONS перед одним выбранным RUN, затем требует
обычный IDLE перед чтением RFID/остатка слота. Проверка RFID отклоняет лишние
или повторные записи до сохранения метаданных.

### Полная LOAD

Загрузка разрешает typed `0x0F`, выбранные стадии `0x10` 0/4/5/6/7, `0x04` PRINT
и свежие наблюдения `0x0A`/`0x08`/`0x05`. Стадия 6 принадлежит только разрешённому
callback датчика головы. Начальный допуск принимает нейтральный BUFFER `0` или
предел пустого буфера `2` и отклоняет `1`/`3`; нейтральный означает отсутствие
активных пределов.

Успешные ответы `0x10` базовой 1.1.3 имеют DATA, зависящие от стадии:

| Стадия запроса | Размер DATA | Данные успешного ответа |
| --- | --- | --- |
| `0` | 1 байт | Режим `0` после обычной инициализации |
| `5` | 4 байта | Значение колеса float32, big-endian |
| `4`, `6`, `7` | 0 байтов | Пустой payload |

Стадия `4` подтверждается до завершения цикла подачи. Приход в голову, стадия
`6` и последующие показания завершают этот путь. Ответы не содержат номера
стадии или ID транзакции; проверка тела по стадии отклоняет несовместимые ответы.

LOAD внутри владеющей пробы задаёт команде продувки `LEN=int(cfg.Tn_extrude)`
(150 мм в базовой конфигурации). Допуск требует целую длину 1–200 мм,
конечные положительные пары скорости/доли, эффективную положительную подачу
не больше 200 мм и фактические коэффициенты скорости/экструзии 1. Результат
подачи false останавливает путь до очистки. Самостоятельные команды сохраняют
настроенные значения по умолчанию.

### Полная UNLOAD

UNLOAD известного источника использует настроенный резак и путь `0x04` IDLE /
`0x11` BUFFER/MATERIAL. Внутри владеющей пробы последовательность втягивания:

1. Завершить выбранный BUFFER и блокирующую помощь головы E−20.
2. Поставить конечную E−30 F600 в очередь и отправить генерацию шагов без ожидания.
3. Отправить один выбранный MATERIAL, пока конечное движение головы может продолжаться.
4. После обычного ACK завершить `M400` до очистки источника и возврата XYZ.

Отправку согласованного хвоста ограничивают проверки горячего нагревателя,
коэффициентов и владения операцией. Ошибка отзывает допуск без повтора или
возврата XYZ. Уже отправленная конечная экструзия может завершиться. Это
согласует два втягивания без предположения об одинаковом физическом старте
моторов. Обычные пути и пути неизвестного источника сохраняют настроенные
последовательности.

UNLOAD неизвестного источника сохраняет обе подсказки источника отсутствующими.
В текущей команде втягивания он разрешает по порядку: свежие `0x08` CONNECTIONS,
`0x08` MATERIAL, `0x0A` STATE, `0x04` IDLE, `0x11` BUFFER с нулевым селектором,
затем `0x11` MATERIAL выбранного канала. Каждый обычный ответ продвигает один
шаг; конфликт масок, потерянный/ошибочный ответ, перестановка или повтор
останавливают путь. Общий селектор ограничен этой командой и фазой.

Полная UNLOAD требует свежих режима `0`, наличия выбранного материала,
нулевого CONNECTIONS, BUFFER `2`, пустой головы, отпущенного резака и очищенного
источника. ACK и кэшированные сведения проверяются отдельно от этих наблюдений
и выхода материала из сопла.

### Втягивание только силами CFS

[Проба только через native](installation.ru.md#native-buffer-trial) по умолчанию
разрешает один выбранный `0x11` BUFFER после IDLE `0x04`/`0001` и свежего обычного
STATE. Явный `TRIGGER=MATERIAL` выбирает MATERIAL; автоматического fallback нет.
Оба варианта не выполняют CUT, XYZ/E и нагрев. Только начальный статус STATE
`0x13` (19) или `0x19` (25) при четырёх байтах данных и режиме `4` допускается
как наблюдение ошибки; последующие ответы должны быть обычными. После обычного
ACK MATERIAL требует свежих режима `0`, нулевого CONNECTIONS, BUFFER `2` и пустой
головы.

В базовой версии статус BUFFER `0x13` означает, что условие пустого буфера
не подтверждено за ожидание прошивки около пяти секунд. Статус MATERIAL `0x19` —
`RETRUDE_ERR6`.
Правильная CRC сохраняет смысл этих ошибок MCU, не превращая их в успешное
втягивание.

Все явные пробы сохраняют владение контекстом/командой и отклонение повторных
событий. Raw-диагностика, другой CFS и автоматическое восстановление не разрешены.
Повторы хоста после CRC/LENGTH отключены; отзыв разрешения хоста не отменяет
исполняющуюся операцию MCU или внутренние повторы штатной библиотеки.

## Ожидания, повторы и отказы

Отдельно фиксируются таймаут транзакции, возможные native-повторы, общий срок
операции, ожидаемое удержание ответа и ожидание датчика. При реализации используем
монотонное время и ожидания, позволяющие reactor работать. Таймауты запросов
закодированы и проверены на ПК; обычные базовые пробы не проверяют истечение
deadline, отмену исполняемой операции или время восстановления на принтере.

Неизвестное показание датчика не превращается в успешную загрузку. Настроенный
материал, сохранённый активный слот или ACK не отменяют противоречивые физические
наблюдения. Покрытие реализации отражается в
[compatibility.ru.md](compatibility.ru.md).
